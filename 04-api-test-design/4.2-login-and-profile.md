# 4.2 · Авторизация и профиль

🟡 надо подумать · тема: токены, негативные кейсы · тестовое задание по ссылке

## Условие

Есть два REST API.

**1. Авторизация** — `POST /auth/login`

```json
// Request
{
  "email": "user@test.com",
  "password": "Password123"
}

// Response
{
  "accessToken": "eyJhbGciOiJIUzI1NiIs..."
}
```

**2. Получение профиля** — `GET /profile`

```
Authorization: Bearer <accessToken>
```

```json
// Response
{
  "id": 152,
  "email": "user@test.com",
  "name": "John Smith",
  "role": "USER",
  "createdAt": "2026-07-01T10:15:00Z"
}
```

Опиши тезисно, в формате «если — то», как будешь это тестировать.

Вопросы по ходу:
- «Может ли прийти ошибка, если мы передаём корректный токен, полученный в прошлом запросе? И это ожидаемое поведение. Как такое возможно?»
- «Будешь расписывать каждый вариант невалидного email отдельным кейсом или используешь маску?»

<details>
<summary><b>Решение</b></summary>

### `POST /auth/login`

- если email и пароль верные → `200`, в ответе непустой `accessToken`;
- если пароль неверный → `401`;
- если такого email нет → `401` с **тем же** текстом ошибки, что и при неверном пароле. Иначе по ответам можно узнать, какие email зарегистрированы;
- если email невалидного формата → `400`;
- если поля пустые или их нет в запросе → `400`;
- если в полях SQL-инъекция или скрипт → `400`, но не `500`;
- если email в другом регистре → уточнить требования, обычно регистр не важен;
- если много неудачных попыток подряд → блокировка или ограничение частоты запросов.

### `GET /profile`

- если токен валидный → `200` и данные владельца токена: `id` и `email` совпадают с тем, кто логинился;
- если заголовка `Authorization` нет → `401`;
- если токен битый или подделан → `401`;
- если схема не `Bearer` (например, `Basic`) → `401`;
- структура ответа по контракту, `createdAt` в формате ISO 8601, `role` из списка допустимых.

### Корректный токен, но ошибка

Токен настоящий и получен только что, но в ответ всё равно `401`/`403`. Это ожидаемые кейсы, и их тоже тестируют:

- **истёк срок жизни токена** — самый частый ответ;
- пользователь вышел из системы (logout) или сменил пароль, и старые токены отозваны;
- пользователя заблокировали или удалили после выдачи токена;
- у пользователя забрали права на этот ресурс.

### Маска или отдельные кейсы

Каждый невалидный email отдельным кейсом не расписывают: чек-лист раздуется без пользы. Делают один кейс «невалидный email → `400`» и набор данных к нему: без `@`, без домена, с пробелом, пустая строка, кириллица. В автотестах это один `@ParameterizedTest` со списком значений.
