# 4.2 · Авторизация и профиль

Тестовое задание по ссылке · тема: токены, негативные кейсы · сложность: средняя

## Условие

Есть два REST API.

**1. Авторизация** - `POST /auth/login`

```json
// Request
{
  "email": "user@test.com",
  "password": "Password123"
}

// Response
{
  "accessToken": "eyJhbGciOiJIUzI1NiIs..."
}
```

**2. Получение профиля** - `GET /profile`

```
Authorization: Bearer <accessToken>
```

```json
// Response
{
  "id": 152,
  "email": "user@test.com",
  "name": "John Smith",
  "role": "USER",
  "createdAt": "2026-07-01T10:15:00Z"
}
```

Опиши тезисно, в формате "если - то", как будешь это тестировать.

Вопросы по ходу:
- "Может ли прийти ошибка, если мы передаем корректный токен, полученный в прошлом запросе? И это ожидаемое поведение. Как такое возможно?"
- "Будешь расписывать каждый вариант невалидного email отдельным кейсом или используешь маску?"

<details>
<summary><b>Решение</b></summary>

### `POST /auth/login`

- email и пароль верные → `200`, в ответе непустой `accessToken`;
- неверный пароль → `401`;
- такого email нет → `401` с тем же текстом ошибки, что при неверном пароле, иначе по ответам можно узнать, какие email зарегистрированы;
- email невалидного формата → `400`;
- поля пустые или отсутствуют → `400`;
- в полях SQL-инъекция или скрипт → `400`, но не `500`;
- email в другом регистре → уточнить требования, обычно регистр не важен;
- много неудачных попыток подряд → блокировка или ограничение частоты запросов.

### `GET /profile`

- валидный токен → `200` и данные владельца токена, `id` и `email` совпадают с тем, кто логинился;
- нет заголовка `Authorization` → `401`;
- токен битый или подделан → `401`;
- схема не `Bearer`, например `Basic` → `401`;
- структура ответа по контракту, `createdAt` в ISO 8601, `role` из списка допустимых.

### Корректный токен, но ошибка

Токен настоящий и получен только что, а в ответ `401` или `403`. Так бывает, когда:

- истек срок жизни токена, это самый частый ответ;
- пользователь вышел из системы или сменил пароль, и старые токены отозваны;
- пользователя заблокировали или удалили после выдачи токена;
- у пользователя забрали права на этот ресурс.

Эти кейсы тоже тестируют.

### Маска или отдельные кейсы

Каждый невалидный email отдельным кейсом не расписывают, чек-лист раздуется. Делают один кейс "невалидный email → `400`" с набором данных: без `@`, без домена, с пробелом, пустая строка, кириллица. В автотестах это один `@ParameterizedTest` со списком значений.
