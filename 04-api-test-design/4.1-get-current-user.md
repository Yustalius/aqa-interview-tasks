# 4.1 · Метод получения текущего пользователя

🟢 разминка · тема: чек-лист по контракту · Озон, технический скрининг

## Условие

> Метод получения информации о текущем пользователе

```
Request:

GET /user

Response:

{"phone": "string",
 "name": "string",
 "email": "string",
 "birthDate": "number",
 "img": "string",
}
```

Накидай тезисы проверок: как бы ты тестировал этот метод.

Наводящий вопрос интервьюера: «Как сервер вообще понимает, кто текущий пользователь?»

<details>
<summary><b>Решение</b></summary>

### 1. Сначала вопросы к контракту

Начинать надо не с перечисления проверок, а с уточнения требований. В контракте есть детали, мимо которых легко проскочить:

- **`birthDate: number`.** Все поля строки, а дата почему-то число. Скорее всего, это timestamp (секунды или миллисекунды от 1 января 1970 года), но это надо уточнить, как и единицы измерения.
- **Висячая запятая после `img`.** Такой JSON невалиден. Это опечатка в документации или так реально отвечает сервер?
- **`phone`.** В каком формате: `+7...`, `8...`, со скобками и дефисами или только цифры? Бывают ли иностранные номера?
- **`name`.** Только имя или полное ФИО?
- **`email`.** Есть ли ограничения по доменам?
- **`img`.** Что это за строка: ID картинки, ссылка на неё? Что приходит, если аватара нет: `null`, пустая строка, поле пропадает?

### 2. Как сервер понимает, кто пользователь

В запросе нет ни ID, ни параметров (не `GET /user/{id}`). Значит, пользователь определяется по **авторизации**: токен в заголовке `Authorization` или сессионная кука. Сервер разбирает токен и отдаёт данные его владельца. Отсюда целый пласт проверок.

### 3. Чек-лист

**Позитивные:**
- валидный токен → `200`, в ответе данные именно владельца токена;
- структура ответа по контракту: все пять полей на месте, типы совпадают;
- значения в ожидаемых форматах: телефон, email, дата рождения, `img`;
- пользователь с незаполненными необязательными полями: что приходит в ответе.

**Авторизация:**
- без токена → `401 Unauthorized`;
- протухший, отозванный, поддельный токен → `401`;
- токен пользователя А не возвращает данные пользователя Б.

Не путай `401` и `403`: `401` — «не знаю, кто ты», `403` — «знаю, кто ты, но доступа не дам».

**Протокол:**
- `Content-Type: application/json`;
- другие методы на `/user` (`POST`, `DELETE`) → `405 Method Not Allowed`, если они не предусмотрены;
- время ответа в пределах требований.
