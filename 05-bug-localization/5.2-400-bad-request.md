# 5.2 · Ошибка 400 в Postman

🟡 надо подумать · тема: валидация, ошибки Spring · Right Line, первый этап

## Условие

> Прилетел такой ответ на запрос в Postman. Что будем делать?

**Запрос**

```json
{
    "orgName": "Рога и копыта",
    "email": "roga.mail.ru",
    "taxNumber": "1234567890"
}
```

**Ответ**

```
HTTP 400
{
    "timestamp": "2025-03-26T10:38:46.226+00:00",
    "status": 400,
    "error": "Bad Request",
    "path": "/api/v3/organisation/register"
}
```

Уточнение интервьюера: «Можешь сказать конкретно, что не так?» Ответа «запрос не прошёл валидацию» недостаточно.

<details>
<summary><b>Решение</b></summary>

**Проблема в запросе.** Самая заметная: `"email": "roga.mail.ru"` — нет `@`, это не email. Скорее всего, бэкенд отбил его на валидации.

Другие гипотезы, которые стоит назвать:
- `taxNumber` похож на ИНН. У ИНН есть контрольная сумма, и `1234567890` её может не пройти. Ещё бывает, что бэкенд ждёт число, а не строку, или другую длину;
- в запросе может не хватать обязательных полей. Это регистрация, а пароля или контактного лица нет. Надо свериться с контрактом метода.

**Проблема в ответе.** Набор полей `timestamp`, `status`, `error`, `path` — это стандартный ответ Spring Boot на ошибку, которую разработчик не обработал сам. Если узнаешь его на собеседовании, это хороший плюс.

В таком ответе нет ни слова о том, что именно не так: ни поля, ни причины. Клиенту приходится гадать. Нормальный ответ на ошибку валидации содержит сообщение или список ошибок по полям: «email: неверный формат». Это отдельный дефект, его стоит завести на бэкенд.

**Что делаю по шагам.**
1. Сверяю запрос с контрактом: состав полей, типы, форматы.
2. Исправляю email и повторяю запрос.
3. Если снова `400`, иду в логи сервиса или к разработчику: из ответа причину не вытащить.
4. Отдельно завожу задачу на информативные ошибки валидации.

</details>
