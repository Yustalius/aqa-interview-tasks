# 8.2 · Разобрать Dockerfile

🟡 надо подумать · тема: Docker · Right Line, первый этап

## Условие

Блок «Docker и docker compose». Опиши, что делает каждая строка.

```dockerfile
FROM bellsoft/liberica-openjdk-alpine:21

LABEL maintainer=qa-team
WORKDIR /app

ADD pcr-mock-app.jar /app/pcr-mock-app.jar
ADD application.yml /app/config/application.yml
ADD logback.xml /app/config/logback.xml
RUN apk update && apk upgrade --no-cache

CMD ["java", "-jar", "/app/pcr-mock-app.jar"]
```

Вопросы по порядку:
1. Что делает каждая инструкция?
2. Чем `RUN` отличается от `CMD`?
3. Что бы ты здесь улучшил?

<details>
<summary><b>Решение</b></summary>

Dockerfile — это рецепт сборки образа: на какой основе собираем, какие файлы кладём внутрь и что запускаем. Даже не зная синтаксиса, большую часть можно понять по английским словам.

### 1. Построчно

| Инструкция | Что делает |
|---|---|
| `FROM bellsoft/liberica-openjdk-alpine:21` | Базовый образ: Alpine Linux с JDK 21 от BellSoft (Liberica — их сборка Java) |
| `LABEL maintainer=...` | Метаданные образа: кто его сопровождает |
| `WORKDIR /app` | Рабочая папка внутри контейнера, создаётся, если её нет |
| `ADD pcr-mock-app.jar ...` | Копирует jar-файл приложения из проекта в образ |
| `ADD application.yml ...`, `ADD logback.xml ...` | Копирует конфиги приложения и логирования |
| `RUN apk update && apk upgrade --no-cache` | Во время сборки обновляет пакеты Alpine (`apk` — пакетный менеджер Alpine) |
| `CMD ["java", "-jar", ...]` | Что выполнить при старте контейнера: запустить приложение из jar |

jar — это вся Java-программа, упакованная в один файл. Её запускают командой `java -jar`, без Gradle и IDE.

### 2. `RUN` и `CMD`

- `RUN` выполняется **при сборке образа** (`docker build`). Результат запекается в образ. Так ставят пакеты и готовят окружение.
- `CMD` выполняется **при запуске контейнера** (`docker run`). Это команда по умолчанию: её можно переопределить при запуске, и в файле работает только последний `CMD`.

Коротко: `RUN` собирает образ, `CMD` говорит, что образ делает, когда его запустили.

### 3. Что улучшить

1. **`COPY` вместо `ADD`.** `ADD` умеет лишнее: скачивать по URL и распаковывать архивы. Для обычного копирования используют `COPY`, а `ADD` только тогда, когда нужна эта магия.
2. **JRE вместо JDK.** JDK — набор для разработки, а чтобы просто запустить приложение, хватит JRE (`bellsoft/liberica-openjre-alpine:21`). Образ меньше, лишних утилит меньше.
3. **Порядок слоёв.** Каждая инструкция — слой, и Docker кеширует слои. `RUN apk ...` стоит поставить **до** копирования jar: сейчас любая пересборка jar сбрасывает кеш, и пакеты обновляются заново при каждой сборке.
4. **`apk update` лишний.** `--no-cache` и так берёт свежий список пакетов и не оставляет кеш в образе.
5. **Относительные пути.** `WORKDIR /app` задан, но пути всё равно абсолютные. Можно писать `COPY pcr-mock-app.jar app.jar` и `CMD ["java", "-jar", "app.jar"]`. Бонус: Spring Boot сам подхватывает конфиги из `./config/` относительно рабочей папки.
6. **Запуск от root.** Контейнер работает от суперпользователя. Лучше создать обычного пользователя и переключиться на него через `USER`.
7. **Нет `EXPOSE`.** Порт приложения нигде не указан, а это заодно и документация образа.
8. **Нет `HEALTHCHECK`.** Контейнер может быть запущен, а приложение внутри — упасть или зависнуть. Healthcheck периодически стучится в приложение, например в `/actuator/health`, и Docker видит, живо ли оно.

Плюс `.dockerignore`, чтобы в контекст сборки не попадало лишнее.

Как это может выглядеть: [`Dockerfile.fixed`](Dockerfile.fixed). Порт и адрес healthcheck в нём условные, их нужно уточнить у разработчиков.

</details>
