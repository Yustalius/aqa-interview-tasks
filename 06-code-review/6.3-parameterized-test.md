# 6.3 · Параметризованный JUnit-тест

🔴 с подвохом · тема: JUnit 5, Allure · Сбер, риск-стратегии

## Условие

Прочитай код и скажи, что будет в результате, **сколько будет тестовых артефактов** и что вообще здесь происходит.

```java
@SpringJUnitConfig(SpringTestConfiguration.class)
@TmsLink("ASDT-T1111")
public class MyTestT1111Tests {

    @TmsLink("ASDT-T1111")
    @ParameterizedTest(name = "{displayName} {index} paramX = {0} paramY = {1} expected = {2}")
    @DisplayName("ASDT-T1111 [MY] Определение param_exit")
    @Link(name = "Test-Case", url = "https://jira.example.com/secure/Tests.jspa#/testCase/ASDT-T1111")
    @CsvSource(value = {
            "false, 0.81, false",
            "true, 0.8, true",
            "true, 0.81, true",
            "true, 0.79, false",
    }, nullValues = "null")
    public void myTestT1111Test(boolean paramX, double paramY, boolean expected) {

        MyRequest request = getRequestFromJson("testData/req.json", MyRequest.class);

        step("Установить paramX, paramY, paramZ", () -> {
            request.getA().setParamx(paramX);
            request.getB().setParamy(paramY);
            request.getC().setParamz("ЮЛ");
        });

        MyResponse myResponse = sendMyAndCheckStatusCode(request, new ObjectMapper().setSerializationInclusion(ALWAYS), 200);

        step("Проверить значение param_exit", () -> {
            Asserter.getAsserter().hardAssertEquals(myResponse.getContext().getParam(), expected, "param_exit");
        });
    }
}
```

Три вопроса по порядку:
1. Сколько тестов будет в отчёте и как они будут называться?
2. Что тест проверяет, своими словами, по шагам?
3. Какое правило зашито в данных `@CsvSource`? Чего в наборе не хватает?

И в конце: что бы ты написал в ревью на этот тест?

<details>
<summary><b>Решение</b></summary>

Код выглядит страшно, но почти всё здесь знакомо: `@ParameterizedTest`, `@CsvSource`, `@DisplayName`, аннотации Allure и шаги `step`. Незнакомые вещи (`Asserter`, `sendMyAndCheckStatusCode`) — это самописные методы проекта, о них достаточно сказать, что они делают судя по названию.

### 1. Сколько тестов и как называются

В `@CsvSource` четыре строки, значит, в отчёте будет **четыре теста**, по одному на каждый набор данных. Имя строится по шаблону из `@ParameterizedTest(name = ...)`:

- `{displayName}` — значение из `@DisplayName`;
- `{index}` — номер запуска, считается с единицы;
- `{0}`, `{1}`, `{2}` — параметры по порядку.

```
ASDT-T1111 [MY] Определение param_exit 1 paramX = false paramY = 0.81 expected = false
ASDT-T1111 [MY] Определение param_exit 2 paramX = true paramY = 0.8 expected = true
ASDT-T1111 [MY] Определение param_exit 3 paramX = true paramY = 0.81 expected = true
ASDT-T1111 [MY] Определение param_exit 4 paramX = true paramY = 0.79 expected = false
```

### 2. Что проверяет тест

1. Берёт шаблон запроса из `testData/req.json` и превращает его в объект `MyRequest`.
2. В шаге Allure подставляет в запрос `paramX` и `paramY` из параметров, а `paramZ` жёстко ставит `"ЮЛ"`.
3. Отправляет запрос и сразу проверяет, что статус `200`. `ObjectMapper` с `ALWAYS` сериализует все поля, включая `null`.
4. Проверяет, что `param_exit` в ответе равен ожидаемому.

То есть тест проверяет бизнес-правило: как сервис вычисляет `param_exit` из двух входных параметров.

### 3. Правило в данных и чего не хватает

`param_exit = true` только если `paramX = true` **и** `paramY >= 0.8`. На порог указывают значения 0.79, 0.8 и 0.81: это граничные значения вокруг 0.8.

Чего не хватает:
- `paramX = false` проверен только при `paramY` выше порога. Нет `false, 0.8` и `false, 0.79`;
- нет значений далеко от границы: `0`, `1`, отрицательных;
- `paramZ` всегда `"ЮЛ"`, поведение для других значений (например, `"ФЛ"`) не проверено.

### Замечания в ревью

1. `paramZ = "ЮЛ"` зашит внутри теста. Его стоит сделать параметром или хотя бы константой с понятным именем.
2. `new ObjectMapper()` создаётся при каждом запуске. Его лучше вынести в поле или в конфигурацию клиента.
3. `@TmsLink("ASDT-T1111")` продублирован на классе и на методе.
4. `nullValues = "null"` объявлен, но `null` в данных нет: мёртвая настройка.
5. В `hardAssertEquals(actual, expected, ...)` стоит проверить порядок аргументов по сигнатуре. Если перепутать `actual` и `expected`, в отчёте будет вводящее в заблуждение сообщение.
6. Имена `MyTestT1111Tests` и `myTestT1111Test` ничего не говорят о сути проверки. Номер тикета уже есть в `@TmsLink`, а имя должно описывать поведение.
7. Только позитивный сценарий со статусом `200`. Нет проверок на невалидные входные данные.
